## Harness kinds

What #307 left covers most clauses: contract and signal waits,
`request_parts`, `hold_next` and `complete_held`, `close_client`, malformed
replies (`status_line`, `framing`, `split`), `mark` and `since`, and
`distinct_from`. A `call` followed by an `expect` reads synchronously,
because the event loop runs only inside waits, so the call returning is
R-WRITE-04's and R-UI-03's barrier.

Seven kinds are added, each with a self-test that fails for the expected
reason before its implementation:

1. **String matchers** in a contract value: `{"non_empty": true}` and
   `{"contains": "..."}`. For R-CONN-03, R-CONN-16, R-WRITE-06 and R-FAKE-03.
2. **Kept values.** A `keep` step stores a member's current value in the
   driver under a label; a `kept` expect checks labels pairwise different,
   or a label the same as the member now. The driver compares with `===`,
   so strings compare by value and models by identity. For R-CONN-03's
   pairwise-different first `readError` values and R-UI-12's same objects
   after an update.
3. **Reads inside handlers.** A `watch_handlers` step names members the
   driver reads inside every counted signal's handler from then on, logged
   per firing. A `handlers` expect checks that every firing of the named
   signals since a mark read those values, and that each fired. For R-UI-06,
   R-UI-08 and R-WRITE-06's "readable inside `writableChanged`".
4. **Stopping the fake**: a `stop` fake op that stops listening, closes
   every client and removes the socket, keeping the records. For R-CONN-06
   and R-WRITE-06's write after the fake is gone.
5. **Assignment**: an `assign` expect that assigns a member from QML and
   holds when the assignment throws. For R-UI-03.
6. **Member types**: a `member_types` expect that reads each named member
   and classifies it as `number`, `string`, `boolean`, `date`, `array`,
   `model` or `function`. For R-UI-02's 24 names with their types and
   R-UI-13's five actions. QML cannot tell an enum from an int, nor see a
   method's parameter types; the notes record that.
7. **The singleton across engines**: a `singleton` expect. The driver
   compares `Tailscale` with the one a component created in the same engine
   resolves; a second engine, with only the module directory on its import
   path and no harness module, resolves `Tailscale` and exits with a code
   saying whether it is non-null and whether it carries a marker the driver
   set on the first engine's `objectName`. For R-UI-01.

## Implementation notes (2026-10-22)

Where the work departed from the plan, and why. Each is also in the
commit that made it.

1. **R-CONN-03 runs in three scenarios of four stagings.** #286 doubles
   its reconnect delay on every loss until an attempt has held for the
   30 s settle (`LocalApiTailscaleBackend.cpp:151`, `:526-536`), so six
   losses in a row wait 0.5 + 1 + 2 + 4 + 8 s, and the last wait would
   come near the harness's wait cap. Three blocks of four
   (`conn-03-reasons-differ-1` to `-3`) wait 3.5 s each and still put
   every pair of the six stagings in one scenario, so each pair is
   compared by a `kept` `distinct` expect.
2. **R-CONN-03's stagings fail `/status` alone.** The requirement stages
   each failure on `/status` and `/prefs`. Whichever fails first sets the
   reason, and the reason names its path, so with both failing the first
   value would depend on which reply #286 read first. Each staging holds
   the next `/status`, then completes it with the failure or closes it,
   and `/prefs` is answered. The scenarios list this under `deferred`.
3. **A short chunk is a chunk that runs past its length line**
   (`2\r\n{}xx...`), #286's "sent a chunk that does not end where it
   said" (`LocalApiClient.cpp:300`), the source R-CONN-03 cites. A chunk
   cut short by the close reads "the connection closed before the
   response ended" on #286, the same as a close mid-body, and the first
   draft's `-3` block failed on exactly that pair.
4. **R-UI-15's backend half is six corpus cases** (`ui-15-1-plain` to
   `ui-15-6-default-router-offline`). A corpus case is a status, its JSON
   Patch edits and the values it publishes, which is the table, so
   appending a health entry to a capture needed no new kind. The cases
   serve prefs `{"WantRunning":true}`, not `{}`: the corpus runner waits
   for `wantRunning`, and no value in the table reads it.
5. **R-WATCH-14's no-ID run is added to evidence.json's `runs`.** The
   status whose `ExitNodeStatus` has no `ID` needs only a positive wait,
   but the runs text left it out and no deferral named it.
   `watch-14-status-object-without-id` runs it.
6. **Each scenario's `deferred` list is evidence.json's**, with the #286
   tests or the reason, plus what the scenario itself leaves out (note 2,
   and R-WATCH-13's first-status `Weird` run: `state` stays `NoState`
   there, so on #286, which never sets `readError` for it, no positive
   wait sees that snapshot).
7. **Tags.** As in #307 (note 4 there), a scenario that runs only clauses
   #286 already meets is `parity` even when its requirement is `fix`:
   `watch-13-snapshot-identity`, the three `conn-03-*`,
   `conn-06-losing-tailscaled-sets-no-state`,
   `conn-14-a-wrong-typed-field-reads-as-default`,
   `write-04-an-action-publishes-nothing`,
   `write-07-a-refused-write-leaves-the-read-side`,
   `write-09-disconnecting-end-to-end`, `ui-02-the-24-properties`,
   `ui-13-the-five-actions` and `fake-03-closing-a-held-write`. The one
   `fix` scenario is `watch-13-unknown-state-is-named`, which fails at
   `unknown-state-named` with `""`: #286 names no unknown `BackendState`
   (`LocalApiTailscaleBackend.cpp:41-55`).
8. **What QML cannot show.** A `member_types` expect reads an enum and an
   int both as `number`, and a method only as `function`, without its
   parameter types; R-UI-02's notify signals are checked by name
   (`<name>Changed` is a function), not by the NOTIFY binding. A second
   #286 singleton is a second backend, which connects to the fake while
   its engine lives, so `ui-01-one-tailscale-per-engine` counts no
   requests after its `singleton` expect.
9. **Every commit compiles.** A format commit that adds a step or an
   expect kind also adds the runner's arm for it, reporting the kind as
   unsupported until the runtime commit replaces it, so the runtime
   self-test fails at that error. `Fake::stop()` landed with its test in
   one commit, because a test calling a method that does not exist
   cannot compile (#320's history had two such commits).
10. **Format test helpers moved.** `scenario_format.rs` was at 729 lines;
    its `full()` scenario and loaders moved to `tests/support/scenario.rs`,
    and the new kinds' tests are in `tests/scenario_kinds.rs`.
11. **Table C's check was renamed**
    (`table_c_lists_the_harness_tests_of_each_requirement_of_its_areas`)
    and covers the six areas; #307's notes doc names the new name.
12. **The bite check.** Each #308 scenario was copied with its last
    acceptance expect's value changed (a string suffixed, a bool or count
    flipped, a type swapped). All 42 copies failed at a value on
    `cpp-286`, none by a timeout. `ui-01`'s `singleton` and the
    `conn-03` `distinct` expects were not mutated; the latter failed at
    a value in the first draft (note 3).
13. **R-CONN-03 waits for each new watch.** `tests/test-tailscale-parity.sh`
    failed once in 50 runs: `conn-03-reasons-differ-1` "steps[25]:
    push_watch_line reached no client". After a loss, #286's reconnect can
    publish `Running` before the fake has its new watch, so a push right
    after the `Running` wait reached nobody. Each staging now first waits
    until the fake has recorded that staging's watch (1 to 4); 20 runs of
    the three scenarios then all matched.
