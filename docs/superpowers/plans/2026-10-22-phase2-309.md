## Decisions

V1. **A view test is a JSON header plus a Rust body.** The header sits in
  `tests/fixtures/tailscale/views/<id>.json`: `format`, `id`,
  `requirements`, `tag`, `evidence`, `clauses`, `deferred`, `body` and
  `on`, with the scenario format's meaning. `body` names a Rust function in
  `plugin/tests/tailscale-parity/src/views/bodies/`. Why: the suite's checks
  are imperative. They compare positions, keep a width or a delegate and
  compare it later, open menus and click inside them. A JSON step language
  for that would be a second programming language. The header keeps what
  the evidence checks and the runner already read: requirements, tag,
  declarations with failing ids and actual values.

V2. **The views come from the reference.** `build-reference.sh` also
  extracts `quickshell/c7shell/` from `a38dbca`, and `--views` prints that
  directory. The runner reads it from `C7_VIEWS_DIR`.

V3. **Each child builds its own import tree** under its private root:
  #286's view files copied from `C7_VIEWS_DIR`, the stand-ins from
  `plugin/tests/tailscale-parity/qml/standins/`, and the theme stand-in with
  its `PaletteStore` generated in Rust from the views' `palette.json`. The
  stand-ins are written from the requirements (R-QML-25, R-QML-27 and
  traceability's "Stand-in" rows), not copied from Quickshell.

V4. **One generic view driver,** `qml/views-driver.qml`: a window holding
  `StatusPill` and `TailscalePopover`, answering `Probe` commands. It knows
  no `ts-` name. Objects cross to Rust as handles, numbered by identity, so
  "the same delegate" is "the same handle". Commands: `get`, `set`,
  `invoke`, `find` (descendants, by `objectName`), `layout` (the layout
  barrier: five `forceLayout()` passes over the popover and the slot),
  `calls` (the stand-in's recorded calls, taken) and `focus`.

V5. **Every mutation is followed by the layout barrier.** The Rust side
  runs `layout` after each `set` and each `invoke`, so every visibility,
  text, colour or width read follows it, as the spec's "Two halves" rule
  says. A recorded-call read happens when the click returns; the barrier
  records no call.

V6. **A check records; a lookup errs.** `check(id, holds, actual)` records a
  failing id with its actual value and goes on. A lookup that cannot
  proceed (no element of a name, two where one is needed) is an error,
  unless the clause is about that count, in which case it is a check.

V7. **Any `.qml:` line in a view child's log is an error,** for R-QML-26's
  "no warning naming a `.qml` file" and R-QML-27.

V8. **Self-tests first,** on a stub view tree under `selftest/views/`:
  the driver's commands, handle identity, the layout barrier, the `.qml:`
  rule and every runner verdict.
