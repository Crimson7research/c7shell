# Plan: Phase 2, PR 2 (#307): transport, parse and group scenarios

**Issue:** #307, under epic #287 (Phase 2).
**Branch:** `test/transport-parse-group-307`, cut from `main` at `920e09f`
(PR #314, #306's fake tailscaled, scenario format and harness).
**Reference:** #286 at `a38dbca`, built by
`plugin/tests/tailscale-parity/build-reference.sh`.

This PR inherits everything in `2026-10-21-phase2-harness.md` (#306): the
fake, the scenario format, the evidence classes and the runner. It runs
every `harness-on-cpp` clause `tests/fixtures/tailscale/evidence.json`
assigns to #307 (`"pr": 307`, and R-HTTP-09's deferred clause) against

## Goal

- Every R-HTTP, R-PARSE and R-GROUP clause assigned to #307 has a scenario
  or a parser corpus case that runs on `cpp-286`. A `parity` one passes; a
  `fix` one fails at a value, with the declared failing ids, their exact
  actual values and a reason naming the #286 `file:line`, never by timeout.
- The harness gains the kinds those scenarios need, each with its runner
  self-test first.
- The traceability lists the test ids of each requirement (Table C), and a
  check keeps that list equal to the test files.

## The owner-approved plan, and what was done

1. **Harness extensions**, each with a self-test commit first that fails at
   runtime for the expected reason, then its implementation:
   - array values (QStringList members such as `issues`) in contract
     waits and expects, and `{"undefined": true}` for "no value";
   - `model` expects and waits: row count, `has_children`, and a row's
     roles by name or by number (`#0` is the display role);
   - per-model signal counters, `peers.rowsInserted` and so on, for
     rowsInserted, rowsRemoved, rowsMoved, modelReset, dataChanged and
     layoutChanged;
   - reply bodies read from capture files (`{"file": ...}`);
   - a served change: a `"times": 1` `/status` rule, an always rule, then
     `push_watch_line`. On #286 any notification with a non-null field
     other than Version, SessionID or Engine starts a new pass
     (`LocalApiTailscaleBackend.cpp:57-70` and `:298-309`), so
     `{"State":6}` is enough.
   Step 4 added three more kinds the scenarios needed (`request_parts`, a
   `mark` step with `since` on a signal expect, and `distinct_from`); see
   note 6. The README's "Kinds added after the plan" documents all of them.
2. **Captures.** `status-idle.json`, `status-exitnode.json` and
   `status-exitnode-offline.json` are copied from #286's fixtures into
   `tests/fixtures/tailscale/captures/`, with `suggest-exit-node.json` and
   `prefs.json` beside them (note 2).
3. **Parser corpus.** 58 cases in `tests/fixtures/tailscale/corpus/`, each a
   status body (a capture or inline JSON, optionally edited by JSON Patch)
   with the expected contract-level output: members, and every `peers` and
   `exitNodes` row with its roles named. The loader
   (`fake-tailscaled/src/corpus.rs`, no Qt) turns a case into a scenario and
   validates it with the scenario rules; Phase 3's `cargo test` reads the
   same files. 46 are `parity` and pass on `cpp-286`; 12 are `fix` and fail
   as declared.
4. **Scenarios.** 20 new files in `tests/fixtures/tailscale/scenarios/`
   (22 with #306's two): 15 `parity`, passing, and 5 `fix`, failing as
   declared.
5. **Traceability.** Table C of
   `docs/superpowers/specs/2026-10-19-tailscale-rust-traceability.md` lists,
   for each of the 41 R-HTTP, R-PARSE and R-GROUP requirements, its evidence
   class, its scenarios, its corpus cases, the PR that runs it, the tests
   declared to fail on `cpp-286` and the classes of its deferred clauses.
6. **Gates.** See "Results".

## Implementation notes (2026-10-21)

Where the implementation departed from the plan, and why. Each is also in
the commit that made it.

1. **roleNames() is not callable from QML** (it is not `Q_INVOKABLE` in
   Qt 6.12). The driver reads a role by name through a `DelegateModel`
   item for the row, as a view does, so the row must exist. A role by
   number goes straight to `data()` and can read off the end, which is how
   `group-05-flat-list` reads row 99. Its `#257` is #286's first user role;
   a rewrite with other role numbers would read no value there whatever
   its model does.
2. **Two more captures**, `suggest-exit-node.json` and `prefs.json`,
   because each corpus case needs a `/prefs` reply and some a suggestion.
   Names, users and addresses were already made up in #286; the node keys,
   numeric NodeIDs and the tailnet's StableID are replaced with made-up
   values, the same way in every file. The string IDs, names and
   addresses the requirements pin are unchanged.
3. **Each child runs with `TZ=<+03>-3`.** #286 reads a date-time without
   a zone as local time, so without a fixed zone the actual values of the
   failing R-PARSE-04 cases would depend on the host. The zone is UTC+3
   with no DST, not UTC: in UTC a keyExpiry built as local time from the
   instant's UTC fields reads right, and the cases with a zone would miss it.
4. **Tags per case and per scenario.** A case or scenario that runs a
   clause of a `fix` requirement which #286 already meets is tagged
   `parity` and declared to pass, because a `fix` one cannot pass on
   `cpp-286`. The evidence checks were relaxed to match (`8ab7b8b` for
   scenarios, the corpus check from the start): a `fix` test names only
   `fix` requirements; a `parity` test may name a `fix` requirement. This
   applies to R-PARSE-04's capture date, nanoseconds, offset, negative
   offset and absent cases, R-GROUP-03's ASCII orders and `group-03-full-not-simple-lowercase`
   (U+0130 against i, where #286's per-unit folding and the full lowercase
   agree but the simple lowercase does not), the passing cases of R-PARSE-07, 09
   and 11, `http-09-403-empty-body`, the four `parse-11-*-clears`,
   `group-10-empty-peer-object-clears` and
   `group-12-needs-login-keeps-rows`. Owner to confirm.
5. **Expected values come from the requirement text**, not from #286: a
   scratch script implemented the rules and each result was checked against
   the acceptance clause. Some cases come from a Statement rather than an
   acceptance example: `parse-04-fraction-dropped-not-rounded`,
   `parse-04-ten-fraction-digits`, `parse-04-offset-without-colon` and
   `parse-04-hours-only-offset` (each fails on #286, whose ISO parser is
   more lenient than the Statement's grammar), `parse-04-one-fraction-digit`, `parse-03-peer-addresses`,
   `parse-09-empty-string-id-never-joined` and
   `group-01-tagged-test-comes-first`.
6. **Three kinds beyond the plan's list**, each with its self-test first:
   `request_parts` checks a request by its start, headers, CRLFCRLF and a
   JSON body against its Content-Length, because byte-for-byte `raw` would
   also pin header and key order, which R-HTTP-02 leaves open; a `mark`
   step with `since` counts a model's signals from just before a change,
   because how many rowsInserted the first fill emits is up to each
   implementation; `distinct_from` checks that `exitNodes` is a different
   object from `peers` (R-GROUP-09).
7. **Signals are counted without their arguments**, so which row a
   dataChanged or rowsInserted names is not checked ("for that row only",
   "at row 1"). The scenarios read the rows after each change instead, and
   list the row argument under `deferred`.
8. **A row expectation reads roles by name**, so an implementation with
   fewer rows than expected fails at `<model>.count` and is then an error
   at the first missing row, not a plain failure. No `cpp-286` fix case
   hits this.
9. **The driver connects to each model member's signals once, at load.**
   That is right for #286's CONSTANT `peers` and `exitNodes`.
10. **Module splits.** `runner.rs` was at 499 lines, so the step runner
    moved to `tailscale-parity/src/steps.rs` and model reads to
    `src/model.rs`; `fake-tailscaled/src/scenario.rs` keeps under 500 with
    `scenario/{model,files,request,check}.rs`.
11. **`Step::Expect` is boxed** (`c42fe49`), because `request_parts` made
    `Expect` large enough to trip clippy's `large_enum_variant`. The four
    commits from `168a789` to `9106871` fail clippy under `-D warnings`;
    squash before review if every commit must pass it.
12. **Table C is new.** Table B maps #286's tests; nothing listed the
    Phase 2 tests. Table C covers the three areas this PR runs; #308 and
    #309 can extend it and its check to their areas.

## Review fixes (owner decisions, 2026-10-21)

Each landed test first, as its own commits.

1. **R-GROUP-10's deferred clauses run here.** The owner moved them into
   #307: each status carries its own tailnet name, so the clause is
   reached by a positive wait on that snapshot, as R-GROUP-12's kept rows
   wait for `NeedsLogin`, and is not a negative after the idle barrier.
   evidence.json's entry now runs both; only the second run's
   `peersKnown` stays `phase3-only`. `group-10-empty-peer-object-clears`
   reads 20 rows, 2 exit nodes, no `rowsRemoved` and `state` `Running` once
   `example.net` is seen (parity). `group-10-running-peer-null-clears` is
   the second run: a `Running` status with `"Peer":null` after
   `{"Prefs":{}}`, expecting 0 rows in both models once its tailnet is
   seen, and failing on `cpp-286` at `peers-cleared` 20 and
   `exit-nodes-cleared` 2. Its status is the small Running status `group-10`
   serves, not `status-idle.json` with a null Peer, because it needs a
   tailnet name of its own to wait for. Table C lists it.
2. **Model query errors** are each checked by their whole message in
   `scenario_format.rs` (`it_names_each_model_query_error_in_full`):
   negative row, empty `distinct_from`, empty name, empty `values`, and
   the role keys `""`, `#`, `#abc` and `#4294967296`. `scenario/model.rs`
   is at 77.78% lines (12 of 54 missed); every missed line is
   `ModelQuery::describe`, which only the parity runner calls.
3. **Reset and layout counts fire.** The stub gained `resetPeers()` and
   `relayoutPeers()`, which emit `peers`' `modelReset` and
   `layoutChanged`; `model-reset-layout` reads each as 1 (self-test 17).
   `group-07`'s same-peers step also expects `peers.layoutChanged` 0.
4. **`parse-04-negative-offset`**: `2027-04-11T05:36:08-03:30` yields
   `2027-04-11T09:06:08Z`, the Statement's `-HH:MM`. #286 reads it right,
   so it is parity and passes.
5. **A reply counted from a mark is served after it.** `group-07`'s
   same-peers step, `group-12`'s NeedsLogin step and `group-10`'s no-Peer
   step expect only zero counts, which a reply served before the mark
   would also give. Each now has a precondition just before its mark that
   exactly one `/status` is recorded, so the reply holding the value its
   wait sees is the second one. The other mark steps each expect a count
   of one, which an early reply fails at a value.
6. **`run_corpus` reports what ran.** `run_all` returns a `Summary`, and
   the corpus line uses its count: `"corpus-pass,corpus-pass"` reports 1
   case, not 2.
7. **No expect repeats its own wait.** `group-09-a-separate-model` no
   longer waits for the 2 exit nodes it then expects; it reads them once
   `state` is `Running` (R-UI-06 fills the models first), so a wrong count
   fails at its value. The other expects that match an earlier wait's
   query (the kept-row counts of `group-06`'s two, `group-10`, `group-12`
   and `group-08`'s `both-back`, and the `still-running` reads) come after
   a served change the wait preceded, so each fails at a value if the
   change alters it.
