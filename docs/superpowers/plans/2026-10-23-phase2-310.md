# Plan: Phase 2, PR 5 (#310): the mutation baseline against #286's C++

**Issue:** #310, under epic #287 (Phase 2).
**Branch:** `test/mutation-baseline-310`, from `main` at `78cd065`.
**Reference:** #286 at `a38dbca`, built by
`plugin/tests/tailscale-parity/build-reference.sh`.

## Goal

- A source mutator applies one operator mutation at a time to #286's
  Tailscale C++, rebuilds, runs the kill suite and records each mutant as
  killed or survived. The repository had no C++ mutation tool
  (`cargo-mutants` covers Rust only).
- The baseline is recorded in the repository. Every surviving mutant has a
  killing test or a written reason it cannot be killed. The score is at
  least the 70% gate.

## Decisions

M1. **The tool is a Rust crate,** `plugin/tests/mutate-cpp/`, a binary and a
  library, with no new dependency beyond `serde` and `serde_json`. It writes
  no C++: it edits a copy of #286's.

M2. **Sites come from clang's AST, through `clang-query`** with the
  reference build's `compile_commands.json`
  (`build-reference.sh` turns on `CMAKE_EXPORT_COMPILE_COMMANDS`). Matchers
  restricted to the file under mutation find binary operators, integer and
  boolean literals and calls standing as statements; the tool reads their
  ranges from `set output dump`. A node from a macro expansion is skipped:
  its text is not at its range.

M3. **The operators:** `==`↔`!=`, `<`↔`<=`, `>`↔`>=`, `&&`↔`||`; an
  integer constant `0`→`1`, `1`→`0`, `n`→`n+1`; `true`↔`false`; a call
  standing as a statement is dropped. One mutant per site.

M4. **The kill suite, cheapest first, stopping at the first failure:**
  #286's six Tailscale QtTest suites through `ctest` (owner decision: they
  are the evidence for the `cpp-suite` requirements), then the scenarios,
  then the corpus. The view tests never load the C++, so they are not in it.
  The harness's test binaries are run directly, so workers do not contend
  for cargo's lock.

M5. **Outcomes:** `killed` (by the step and test named), `timeout` (killed,
  counted apart), `survived`, `build-failed` (not a valid mutant, excluded
  from the score). Score = (killed + timeout) / (killed + timeout +
  survived).

M6. **Workers:** each has its own copy of the reference tree and its own
  CMake build, built once. A mutant is applied, built, run and reverted in
  one worker; four workers run at once.

M7. **The record:** `tests/fixtures/tailscale/mutation/baseline.json`, with
  the source commit, the operators, every mutant (id, file, line, column,
  from, to, outcome, the killing test) and, for a survivor, either `reason`
  or `killed_by_added`, the test this PR adds that kills it. A run resumes
  from the file. `tests/evidence.rs` checks the record: every survivor
  accounted for, and the score at least 70%.

M8. **Self-tests need no C++ written here:** the dump parser runs on
  captured `clang-query` output, the editor on strings, and the runner on a
  project of plain files whose build and test steps are shell commands. One
  live test finds the sites of #286's `StatusParser.cpp` when the reference
  is built.

## Order

1. The dump parser and the site finder, test first.
2. The editor and the operator table.
3. The runner: workers, the kill pipeline, outcomes, resume.
4. `build-reference.sh` exports compile commands; the CLI.
5. The baseline run; then each survivor: a killing test or a reason.
6. The record's checks; the gates.

## Implementation notes

- **The baseline.** 297 mutants of a38dbca: 192 killed and 105 survived,
  a score of 0.646 under the 70% gate. All 105 survivors were in code
  #286's suites reach only through the transport: `LocalApiClient.cpp`
  (59), the backend (25), `StatusParser.cpp` (12) and `PeerModel.cpp` (9).
  The first full run, on four workers, was stopped for low memory after
  114 mutants; it resumed on two, and `restore()` put back the files the
  stopped run had left mutated.
- **The killing tests.** 15 scenarios, each running a backend half of a
  requirement through QML by positive waits, kill 29 survivors (28 killed,
  1 timed out): R-HTTP-03, -04, -05, -07, -08, R-WATCH-03, -09, R-CONN-04,
  R-CONN-06 and R-GROUP-06. evidence.json gives each a `harness-on-cpp`
  deferred clause with `pr` 310, and Table C lists them. The score is
  0.744 (221 of 297); without the added kills it is still 0.646.
- **What review changed.** A fifteenth scenario, a reply that is the blank
  line alone, was dropped: the requirements do not decide whether a blank
  line before the status line ends the head, so it pinned #286's reading,
  and its two mutants carry that as their reason. Expectations that read a
  value no positive wait had shown were dropped, and the ones naming #286's
  wording where a requirement names less were narrowed. Every added kill
  was run again against the revised scenarios. A review of each reason
  against #286's source found `297:31`/`297:33` killable by R-HTTP-05's own
  `2\r\nabXY`, which a scenario now runs, and corrected the reasons of the
  pending-half resets (a pass a notification opens between a loss and its
  retry), the dropped sort (the first-match joins by id), the blank first
  line, and `PeerModel.cpp:157:69`, whose kill needs the harness to read a
  signal's arguments.
- **The timeout.** `LocalApiClient.cpp:325:25` (`remove(0, …)` to
  `remove(1, …)`) spins in emitLines() on an empty watch line, whose body
  `\n` it never shortens; `watch-03-a-blank-line-emits-nothing` pushes one.
  A timeout now runs again like a failure, and this one timed out both
  times.
  The record names it as that scenario's, and `baseline.rs` accepts an
  added kill that is a timeout in the step that runs its kind.
- **The reasons.** 76 survivors stay, each with a reason in the record:
  `equivalent:` (no input changes what a caller observes), `needs …`
  (only a Phase 3 barrier, the clock or the retry hook tells it apart;
  mostly the settle timer and the read barrier) or `unfixed:` (both meet
  the requirement and differ only in what no requirement decides, such as
  a reason's quoting).
- **A push needs one connected client.** `push_chunk` writes to every
  client that takes pushes, the watch and any open read alike, so a raw
  chunk pushed while a pass is out also lands on that pass's socket. Each
  push waits for `connected: 1`, as conn-16 does; `push_watch_line` writes
  to the watch alone.
